# 障害予防の修正と反映手順

## 修正内容

- Notion設定の取得失敗・Notion投稿失敗・集計送信失敗を成功扱いにしない。集計、Notion、ダッシュボードの順で保存し、最後のレポート保存を完了の記録とする。社員単位の投稿失敗は他の社員を止めず、全体では非ゼロ終了する。
- アップロードごとに版IDを発行し、ログ取得時の `X-Upload-Version` を分析元として引き継ぐ。分析中に新しいアップロードがあれば、古い分析結果の保存後もpendingに残る。同秒内の更新も区別する。旧データは次回アップロードまで従来の時刻比較を継続する。
- pending取得は既定90日まで遡る。`REPORT_LOOKBACK_DAYS` で変更できる。成功済みで変更のない社員には分析を実行しない。
- 社員PCの保存済み未送信ログは直近90日から1回最大10件再送する。直近3日分は従来通りActivityWatchから再取得する。正しい成功応答を確認した場合だけ送信済みハッシュを保存する。
- AIの空配列、別社員、重複社員、不正な数値・タイムラインを保存前に拒否する。存在しない `generate-report.ts` を指すnpmコマンドも修正した。
- Notion本文は全ページ取得し、新本文の保存後に旧本文を削除する。追加失敗時に旧本文を消さず、削除失敗も通知対象にする。大きい表は見出しを繰り返して分割する。
- 主要な外部通信にタイムアウトを設定する。sharpは0.35.4に限定更新し、依存パッケージ検査の指摘を解消した。

Notion本文の分割とページネーションは[Append block children](https://developers.notion.com/reference/patch-block-children)と[Pagination](https://developers.notion.com/reference/pagination)を参照した。

## 検証

`npm test` は投稿失敗・設定取得失敗・AI出力不正・Notion本文の途中失敗・全ページ取得・表分割・分析元の版引き継ぎを検証する。
`npm test --prefix dashboard` は既存テストに加え、実際のWorkerルートをSQLiteの全migration適用済みDBとメモリ上のR2代替で実行する。
分析中の再アップロード、旧publisher、旧データ互換、認証拒否、保存済みログの再送を確認する。
これはローカルの検証であり、本番D1/R2/Notionへの書き込み、社員PCの実機更新、VPS cronの動作確認ではない。

## 本番への反映順

1. 稼働中の集計ジョブを停止し、実行完了を待つ。現行の配置commit・D1のバックアップ・cron設定を控える。
2. D1へ `0008_report_source_version.sql` を通常のmigration手順で適用する。追加列だけなので既存データは削除しない。
3. Workerと管理者/VPSの `report/` を同じ修正版へ更新する。旧publisherは版IDを返せず、新しいアップロードがpendingから消えないため、片方だけを更新した状態で定期実行を続けない。
4. ダッシュボードをビルドして社員向けエクスポーターを公開する。既存社員PCのファイルは自動更新されないため、導入済みPCにも更新が必要。
5. テスト用社員・テスト用Notion DBで送信、集計、Notion保存、pending解除を確認する。途中失敗を注入し、再実行で回復することを確認してからcronを再開する。

ロールバックは旧Workerと旧reportを揃えて戻す。追加列は残してよい。社員PCの更新状況も記録する。

## 残る制約

- cronや手動実行の多重起動を防ぐホスト側ロックはこのリポジトリに含まれない。Notionには一意制約がないため、別ホストを含む同時投稿や作成応答の喪失では重複ページが生じ得る。実行ホストの一元化と排他が必要。
- NotionとD1/R2は共通トランザクションではない。途中失敗は未完了として再実行するが、一時的に新旧の本文が並ぶ場合がある。Notionスキーマ自動移行の中断復旧は今回変更していない。
- R2の本文保存とD1のアップロード記録は別操作である。途中障害時には社員側の再送に依存する。APIへの同時アップロードの到着順序までは保証しない。
- PCに書き出されていない過去日のログや、90日を超えた失敗は自動復旧対象外。保持期間が90日以外の場合は集計の遡及日数と合わせて運用する。
- 稼働ログを議事録システムへ自動投入する実装はない。両者のNotion DB・認証・ジョブの役割を混同しない。

再開時は本書、`report/publish-report.mjs`、`report/notion-api.mjs`、`dashboard/src/server/worker.ts`、`agent/export-daily-log.ts` とGitHubの変更差分を確認し、まず本番の配置とcronの排他状態を照合する。
